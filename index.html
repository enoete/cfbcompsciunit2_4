Warm-up

Why do we need a life cycle at all?

The Software Development Life Cycle (SDLC) is a structured framework for planning, creating, testing, deploying and maintaining a system. Think of it as a recipe. There's more than one way to make goat water, but every good cook still buys the ingredients before lighting the fire.

🍲 The recipe analogy

You can cook from a fixed recipe (plan everything first), taste-and-adjust as you go (iterate), or start from a store-bought seasoning mix and add your own touch (reuse). Each SDLC model is a different recipe style. Same kitchen, same ingredients, different order and different amount of tasting along the way.

The big picture

Every model is a remix of the same six moves

Before Waterfall, Spiral and the rest, there's one generic skeleton underneath all of them. Every model you'll meet is just a different opinion about how strictly you follow this order and how often you're allowed to go back.

🎭 Making a mas costume, start to finish

Feasibility: can the troupe afford sequins and feathers for 400 people this year? Requirements: the band leader announces the theme, colours and sections. Design: the designer sketches each section's costume. Implementation: the mas camp sews night after night. Testing: fittings, because a headpiece that falls off on the road is a failed test. The models

Seven recipes for building software

Your syllabus names the waterfall approach, evolutionary development (including prototyping), the fountain approach, formal transformation and the reuse-oriented approach. We'll add the Spiral model, plus a quick look at Agile and Incremental, because they show up in real projects and case studies. Each tab has a hands-on simulator. Work through all of them.

🌊 The Waterfall Model

The oldest and most linear model. Phases happen in a sequential, unbreakable order, like water going over a fall: it only flows down. A project begins with feasibility analysis; once feasibility is demonstrated, requirements analysis begins, and so on. It was the first model to clearly mark the end of one phase and the start of the next, with documentation, verification and validation at each boundary.

🏠 Building a house

You can't put the roof on before the walls, or the walls up before the foundation. Changing the foundation after the walls are up means tearing them down. In Waterfall, changing requirements after coding is just as painful.

1. Requirement analysis & definition→2. System & software design→3. Implementation & unit testing→4. Integration & system testing→5. Operation & maintenance
What happens in each of the five phases

1. Requirement analysis & definition. The developer investigates what users need and writes a developer's version of the requirements. Because users often can't describe their needs precisely, the developer gets users to accept a proposal before work continues. Deliverable: an agreed requirements document. (Like a detailed shopping list before the market.)

2. System & software design. High-level design (which programs are needed and how they interact), low-level design (how each module works), interface design (what the screens look like) and data design (what data is needed). The overall architecture is defined. (The house blueprint.)

3. Implementation & unit testing. Designs are translated into code, written by hand or by code generators. Each module is tested on its own. (Building and checking one room at a time.)

4. Integration & system testing. Modules are combined, and the whole system is tested with expected data to check it does what the user requires. (Does the plumbing connect? Does power reach every room?)

5. Operation & maintenance. The delivered system changes over time: bug fixes, changes driven by user input, enhancements. (Fixing leaks after you move in.)

Verification & validation at every boundary. At the end of each phase the output is checked: is it complete and consistent with its input (the previous phase's deliverable), and is it consistent with the overall requirements? Only then does it flow down.

✅ Strengths
  • Easy to explain to the user; simple and easy to use.
  • Stages and activities are well defined, with clear milestones.
  • Verification at each stage helps detect errors and misunderstandings early.
  • Easy to manage: each phase has specific deliverables and a review.
  • Works well for smaller projects where requirements are very well understood.
⚠️ Weaknesses
  • Adjusting scope during the life cycle can kill a project.
  • No working software is produced until late in the life cycle.
  • High risk and uncertainty: problems may not surface until testing.
  • Very rigid; does not reflect the iterative way software is really built.
  • Assumes requirements won't change and must all be specified up front, so it suits automating an existing manual system, not brand-new systems with hidden or unknown requirements.

⚡ Rapid Prototyping

A working model of the software with limited functionality is built quickly, usually focused on the user interface, so users can evaluate the developer's proposals and try them out before the real thing is built.

🪶 The sample costume

No mas camp sews 60 identical costumes from a sketch. They build one sample in cheap fabric, put it on a model, let the band leader react ("more feathers!", "that headpiece blocks the view"), adjust, and only then cut the expensive material. The sample costume is the prototype. Movie trailers and car show models work the same way.

1. Requirements planning→2. User description→3. Construction→4. Cutover
The four phases explained

1. Requirements planning: a workshop with structured discussion of the business problem.

2. User description: automated tools capture information from users.

3. Construction: productivity tools (code generators, screen generators) build the prototype quickly.

4. Cutover: installation of the system, user acceptance testing and user training.

✅ Strengths
  • Reduced cycle time and improved productivity; fewer people means lower cost.
  • A time-box approach mitigates cost and schedule risk.
  • Customer involved throughout, minimising the risk of not meeting business needs.
  • Uses modelling of business, data and processes; users get an early feel for how the real software will work.
⚠️ Weaknesses
  • The accelerated process must give users quick responses.
  • Risk of never achieving closure (endless "one more change").
  • Needs a system that can be modularised.
  • Developers and customers must commit to rapid-fire activity in a short time.
  • "Rapid" is relative: a prototype can take hours or days.
  • Clients may mistake the prototype for the finished product.

🌱 Evolutionary Development

Instead of producing one complete requirements specification that is approved in one go, you evolve the system through a series of versions. Each version goes to users; their feedback shapes the plan for the next version. The aim is a mature system reached through a series of prototype iterations. It is especially effective for new systems, where requirements can't be fully known up front.

📝 Writing an essay

You write a rough draft, get comments from your teacher, revise, get more comments, revise again. You never throw the essay away; it just keeps getting better. That's evolutionary development. (Contrast the costume sample in Rapid Prototyping, which is often thrown away.)

Grow TroupeTrack, one release at a time

You release a version, masqueraders use it, feedback pours in. Each round you can only build two improvements. Pick the ones real users are asking for most, and watch the "fit to needs" meter.

✅ Strengths
  • Constant updates driven by user input mean the program mostly fits the real need.
  • Flexible: changes are welcomed throughout.
  • Continuous user involvement.
⚠️ Weaknesses
  • The process can be extensive because of constant feedback.
  • There can be a gap in the functionality expected by management, developers and end users.
  • Hard to tell when the system is "complete".

🌀 The Spiral Model

A combination of the Waterfall model and rapid prototyping, with risk analysis. Development goes round and round in loops; each loop passes through four quadrants. Based on the project's unique risks, the team may borrow elements of other models (incremental, waterfall, evolutionary prototyping) inside the loops.

🎮 Alpha, beta, release

Game studios ship an alpha (high risk, lots of bugs), then a beta (medium risk, more features), then release candidates, then the full release. At every stage they ask "what could sink us now?" and deal with it before spending more. Each stage is one loop of the spiral.

✅ Strengths
  • The initial design doesn't have to be perfect.
  • Users can be tied to every step; early and frequent feedback.
  • Costs are assessed frequently.
  • Continuous risk assessment catches problems early.
⚠️ Weaknesses
  • Time spent evaluating risk is too much for small or low-risk projects.
  • Planning, resetting objectives, risk analysis and prototyping can be excessive.
  • Complex; needs real risk-assessment expertise.
  • The spiral may continue indefinitely, and it can be expensive.

🔬 Formal Transformation

A mathematically based technique for the specification, development and verification of hardware and software. It is similar to Waterfall (each phase finishes before the next) but the specification is written as a mathematical model and transformed, step by provable step, into code. It can prove properties of a system without running it. Used where safety, reliability and security are critical.

1. Requirements definition→2. Formal specification→3. Formal transformation→4. Integration & system testing→5. Maintenance
What happens in each phase

Requirements definition: requirements are formally expressed. Formal specification: requirements and specifications are combined and expressed mathematically. Formal transformation: design, implementation and unit testing are carried out using mathematical notation. Integration & system testing: the system is deployed into its environment and tested. Maintenance: the system is monitored, upgraded and updated.

🧮 Testing vs proving

Checking 2+2, 3+3 and 5+5 doesn't prove addition always works. A maths proof covers every case. Testing software is checking examples; formal transformation is the proof.

⛲ The Fountain Model

Named after a fountain, where water rises and falls back to the pool below, again and again. It was developed to support object-oriented development. It accepts that there is considerable overlap of activities: the movement from analysis to design to implementation is interwoven with iterative cycles across those phases.

✏️ Revising an essay

You draft the introduction, start the body, jump back to fix the intro, push on with the body, sketch the conclusion, then fix the body again. Nothing is truly "finished" until the end; everything overlaps. Building object-oriented classes feels exactly like this.

✅ Strengths
  • Supports the iterative nature of software development within phases.
  • Recognises overlap of activities across the cycle.
  • Supports incremental development, focusing on subsystems.

⚠️ Weaknesses

♻️ Reuse-Oriented Development (ROD)

Systems are built from pre-existing code and components, from commercial products or open-source (OSS) systems, instead of writing everything from scratch. In its pure form it's not always practical, but done carefully it saves time and keeps bugs out of the first release, because the components have already been tested elsewhere.

🧩 The slide-deck template

You don't design every slide from a blank page; you start from a template with layouts already done and fill in your content. Or think of a kitchen: you buy ready-made cabinets and fit them, instead of cutting timber. ROD builds software the same way.

1. Requirements definition→2. Component analysis→3. Requirements modification→4. System design with reuse→5. Development & integration→6. System validation

The component shop

Writing TroupeTrack from scratch will take 24 weeks, but Sugar Mas registration opens in 14. Add ready-made components to your cart to get under the deadline, and read the fine print: every component brings a risk with it.

✅ Strengths
  • Increased reliability: components have already been deployed and tested in many settings.
  • Reduced development time and cost; less to build.
  • Components often follow industry standards.
⚠️ Weaknesses
  • Source code is often inaccessible, increasing maintenance costs; you can't fix their bugs.
  • Finding and adapting components can be tedious and time-consuming.
  • Compatibility issues; limited customisation.
  • Dependency risk if a vendor discontinues a component.

🏃 Modern cousins: Agile & Incremental

Not named in your syllabus list, but you'll see them in the case studies and in every job advert, so know what they are.

🏃 Agile

Work happens in short cycles called sprints (often 2 weeks). Working software is delivered after every sprint, and each build adds features; the final build has everything the customer needs. Great for changing requirements and frequent customer feedback. Close relative of evolutionary development.

📈 Incremental

The system is split into modules that are designed, built and delivered one at a time. The core goes live early; each increment adds a piece. Great when early delivery of core features matters. (Think: open the mas camp's registration first, add costume payments in increment 2, pickup tracking in increment 3.)

✅ V-Model (mentioned in case studies)

A Waterfall variant where every development phase on the way down has a matching testing phase on the way up (requirements ↔ acceptance testing, design ↔ system testing, and so on). Popular for banking and safety-critical systems because testing is planned from day one.

Phase 1

Feasibility: can we build it, and should we?

The feasibility study is focused on the goals of the organisation. It analyses whether the project can practically be created, and above all whether it would be financially and technically feasible to develop. If the feasibility report is positive, the next phase (gathering requirements) begins.

🚗 Buying your first car

(1) Can I afford it, including insurance and gas? Economic. (2) Can I actually drive and maintain it, and does a mechanic nearby stock the parts? Technical. (3) Will it really fit my life, and will my family use it? Operational. A feasibility study asks the same questions of a software project before anyone writes code.

⚙️ Technical feasibility

The technical solution and its constraints: will the proposed equipment and software satisfy the user requirement?

  • Do we have the expertise?
  • Is the technology mature and available?
  • Can current infrastructure support it?

💰 Economic feasibility

Compares costs with benefits: estimate the savings and benefits expected, compare with costs. If benefits outweigh costs, design and implement; otherwise justify further or find an alternative.

  • Development + running costs?
  • Expected benefits and savings?
  • Return on investment?

👥 Operational feasibility

Are the human resources available to operate the system once installed? Will people actually use it?

  • Do users want it?
  • Can they use it effectively?
  • Does it fit current processes and culture?
Many textbooks extend these three into TELOS: Technical, Economic, Legal (does it break any law or regulation, such as data protection?), Operational and Schedule (can it be ready in time?). A project can pass four and still fail on the fifth.

Phase 2

Requirements gathering: finding out what they actually need

Once feasibility is positive, the team communicates with the stakeholders to learn what the software should provide and which features to include. Requirement elicitation techniques (interviews, questionnaires, observation, review of internal documents and prototyping) are the tools for this.

🎂 Ordering a birthday cake

"Something nice" is not a requirement; it's a feeling. A good baker asks follow-up questions (interview), sends a quick form to the guests about flavours (questionnaire), watches how the family eats at parties (observation), checks last year's order slip (document review) and bakes a tiny sample (prototyping). Only then does "something nice" become "three tiers, lemon, no nuts, serves 40, ready 3 pm Saturday."

👥 Interviews

An interview is questioning a person, a conversation in which information is elicited. Interviews are a strong way to collect requirements, and organisations may use several types (structured, unstructured, one-to-one, group).

Reasons for using interviews
  • Investigate issues in depth.
  • Discover how individuals think and feel about a topic, and why they hold certain opinions.
  • Inform decision making, strategic planning and resource allocation.
  • Allow discussion of sensitive topics people may not raise in a focus group.
  • Add a human dimension to impersonal data.
  • Deepen understanding and explain statistics collected by questionnaires.
✅ Advantages
  • Detailed information about feelings, perceptions and opinions.
  • More detailed questions can be asked.
  • Usually a high response rate.
  • Ambiguities can be clarified and incomplete answers followed up.
⚠️ Disadvantages
  • Very time-consuming: setting up, interviewing, transcribing, analysing, feedback, reporting.
  • Can be costly.
  • Only reaches a few people.

    📝 Questionnaires

    An inexpensive way to gather data from a potentially large number of respondents. Often the only feasible way to reach enough people for statistical analysis.

    Reasons for using questionnaires
    • Patterns, frequency, ease and success of use.
    • User needs, expectations, perspectives, priorities and preferences.
    • User satisfaction with services.
    • Shifts in user attitudes and opinions.
    • Relevance of services to user needs.
    ✅ Advantages
    • Relatively easy to analyse.
    • A large sample can be reached at low cost.
    • Simple to administer; familiar format.
    • Quick for respondents; standardised answers.
    • Respondents have time to think.
    ⚠️ Disadvantages
    • If you forget a question you usually can't go back, especially if anonymous.
    • Hard to get enough responses.
    • Respondents may skip questions or complete them incorrectly.
    • Can feel impersonal.

    👀 Observation

    Watching people in their natural setting, during their normal everyday work. Two types: non-participant observation (the analyst watches without taking part) and participant observation (the analyst joins in the activity).

    ✅ Advantages
    • Helps overcome issues of validity: you see what people do, not what they say.
    • Useful when users can't provide certain information, or may give inaccurate information.
    • Supplements other methods; simple.
    ⚠️ Disadvantages
    • Can't easily measure attitudes or opinions.
    • Time and cost are high; small sample.
    • Incomplete for complex jobs.
    • May interfere with job performance, or people act differently when watched (bias).
    • Needs a skilled observer; validity and reliability can be problematic.

      Requirements analysis tools

      Once information is gathered, analysts model it with these tools. You'll draw the first two for real in the next lesson.

      🌊 Data Flow Diagram (DFD)

      Documents the flow of information and the storage of data through a system: from input, through processes, into storage, out as output.

      📖 Data dictionary

      Gives the name, type, size and description of all the relevant data used in the system. A central reference everyone agrees on.

      🧠 Semantic data model

      Models data in the context of its interrelationships with other data; an abstraction defining how stored symbols relate to the real world. Also called a conceptual data model.

      📦 Object models

      Store specific information about entities as objects with properties (attributes) and behaviours (methods), close to how we think about real things.

      🛠️ CASE tools

      Computer Aided Software Engineering tools analyse present data and model the system, automating diagrams, documentation and even code generation.

      Phase 2, wrap-up

      Functional vs non-functional, and getting requirements right

      🎯 Functional requirements

      • Describe the interaction between the system and its environment.
      • Describe how the system should behave given certain inputs.
      • Answer questions independent of how the solution is implemented.

      "The system shall let a masquerader register for a section."

      🧱 Non-functional requirements (constraints)

      • Put restrictions on the system that limit our choices for building a solution.
      • Can limit the programming language, platform, tools or techniques.
      • Cover speed, security, reliability, usability, cost.

      "Any page shall load in under 3 seconds on a 4G phone."

      🎮 The games console

      Functional: what it does (plays games, connects online, saves progress). Non-functional: how well (loads in under 10 seconds, 4K, runs quietly, under 200 W, costs under $500).

      Sort TroupeTrack's requirements

      Software requirement validation

      After requirements are developed they must be validated. Users might ask for illegal or impractical features, and experts may misread needs. Each requirement is checked:

      ✅ Practically implementable?
      Can it actually be built?
      ✅ Valid for functionality?
      Does it belong to what this software is for?
      ✅ Unambiguous & complete?
      One meaning only; nothing missing.

      Three validation techniques: requirements review (a manual process where several readers from the client and contractor check the document for anomalies and omissions), prototyping (an executable model shown to users to see if it meets their real needs) and test-case generation (if a test is hard or impossible to design, the requirement will probably be hard to implement and should be reconsidered).

      Client: a regional bank with 50 branches and 200,000 customers. Project: replace a 15-year-old legacy core banking system. The old system is stable and handles basic transactions well, but it can't support mobile banking, real-time processing, or modern payment methods like digital wallets.

      Model: Waterfall, or its V-Model variant. Requirements are well defined and stable (regulations don't change mid-project); banking systems need extensive testing and validation at each phase; documentation is critical for audits; changes mid-development would be extremely costly and risky.

      Why not Agile? Regulations require complete specifications up front, and iterative deployment of a core banking system risks breaching them.

      Elicitation: review internal and regulatory documentation; interview compliance officers and managers; questionnaires for the large employee base; prototyping for the user interface only after core requirements are locked.

      Client: a startup with $2M seed funding. Project: a platform mixing photo sharing, short video and group chat, aimed at ages 13–24. The founders have a vision but aren't sure which features will land. They want to launch fast, beat competitors and iterate on feedback. Six months to a Minimum Viable Product (MVP).

      Budget$2M for build, servers and marketing
      Team4 developers, 1 designer, 1 product manager
      RequirementsUncertain; users can't say what they want
      MarketCompetitors ship features weekly
      Goal100,000 users in 6 months, or no more funding

      💻 Lead Developer"Use proven tech. Don't reinvent the wheel."
      🎨 UX Designer"If they don't love it in ten seconds, they delete it."
      💼 Investors"Show us growth and engagement in six months."

      💡 Instructor discussion points

      Model: Agile (Scrum or Kanban), a close cousin of evolutionary development. Requirements are unclear and will evolve; speed to market matters; two-week sprints allow rapid course correction. Prototyping also works for early requirements: quick mock-ups tested with focus groups.

      Elicitation: prototyping and observation; interviews may not work well with teens. Use mock-ups, observe how they use existing apps, beta test with small groups, A/B test features.

      Reuse: strongly recommended for authentication, video processing, messaging and content delivery; it saves months.

      Typical MVP: profiles, photo/video sharing, direct messaging and a basic feed. Save AI recommendations, live streaming and advanced filters for later iterations.

      🚑 Case 3 · MedAlert: emergency dispatch system

      Client: a city emergency services department. Project: a mission-critical system coordinating ambulances, fire trucks and police, integrated with 911 call centres, hospitals, GPS tracking and traffic data. The current 20-year-old system crashes often; response times are up 30% this year. After a system failure contributed to a preventable death, the council approved a $10M emergency budget.

      Failure toleranceZero: downtime costs lives
      Timeline12 months (election pressure)
      Integrations30+ legacy systems, poorly documented
      Operations24/7; can't go offline for updates
      RegulationsHealthcare, criminal-justice and emergency-comms rules
      UsersWork under extreme stress
      🚒 Fire Chief"Real-time GPS on every unit, plus building blueprints."
      🚓 Police Chief"Security first. Criminals must never see unit locations."
      🏥 Hospital Director"Send patient vitals ahead. Every second counts in trauma."
      ☎️ 911 Manager"Operators need it intuitive under pressure. The old one takes 40 hours to learn."
      🏛️ City Council"It must work perfectly. Results in 12 months."
      🔐 IT Security Officer"Critical infrastructure: redundancy, disaster recovery, bulletproof security."

      1Which approach fits best?

      2Design the four spirals

      Drag each loop's focus into the right spiral, in the order that tackles the biggest risk first.

      3Stakeholder priority ranking

      When requirements conflict you must prioritise. Drag the categories into rank order, 1 = highest.

      4Is the 12-month schedule feasible?

      5Elicitation under stress

      Which techniques should the team use with dispatchers and responders, and which should they avoid?

      Is there ever a "perfect" model for a project this complex? What safeguards (redundancy, failover, testing, rollback, training) must be in place?

      💡 Instructor discussion points

      Best approach: Spiral, or a hybrid Spiral–V model. High risk makes systematic risk analysis essential every loop; 30+ integrations need incremental validation; regulations need thorough documentation; stakeholders can negotiate trade-offs as they see each loop's prototype.

      Sample spirals: 1 core dispatch + basic GPS (can we hit the response time?); 2 hospital integration (healthcare data security); 3 criminal databases and blueprints (legacy integration); 4 full integration, redundancy and deployment (failover and training).

      Priorities: life safety first (reliability and speed), then security, then usability, then integration breadth. Make trade-offs transparently.

      Schedule: 12 months is very aggressive; 18–24 is realistic. If forced, deploy the core in 12 months and phase in the rest.

      Elicitation: ride-along observations, simulated emergencies, interviews in calm periods, prototypes with feedback. Avoid relying on questionnaires; they won't capture the stress.

      Most realistic: buy commercial software. Nine months is too short for a robust custom LMS; $1.5M barely covers development, never mind maintenance; commercial platforms are refined by thousands of institutions; vendors handle security patches and updates.

      🏠 Case 5 · HomeMind: AI smart-home ecosystem

      Client: a mid-sized company entering the smart-home market against the tech giants. Project: custom hub and sensors plus an AI that learns household behaviour and automates lighting, temperature, security and entertainment. Hardware + software + machine learning, with privacy concerns and hundreds of third-party devices.

      DeadlineTrade-show launch in 10 months
      DependencySoftware can't be fully tested until hardware prototypes exist
      AILearning behaviour is somewhat unpredictable
      EcosystemMust work with 100+ devices
      UpdatesOver-the-air firmware for thousands of homes
      📦 Product Manager"Our edge is AI that truly learns."
      🔧 Hardware Engineer"Firmware and software must be in perfect sync."
      🔐 Security Expert"We're inside people's homes. One breach ends us."
      🎨 UX Designer"Setup must be grandma-friendly."
      📣 Marketing"We launch at the trade show. Full stop."

      One model can't fit all four components. Drag a model onto each component.

      2Testing a system that learns

      "Input X, expect Y" doesn't work for machine learning. Match each testing technique to what it's for.

      5Deep reflection

      Why might a company invent a hybrid approach? What are the risks of leaving textbook models behind? How would you convince stakeholders?

      💡 Instructor discussion points

      Hardware: V-Model or Waterfall. Hardware changes are expensive; physical prototypes go breadboard → PCB → final.

      Core platform: Incremental with Spiral elements. Critical networking and security first, rigorously tested; spiral risk analysis for encryption and device communication.

      AI/ML: Prototyping + Agile. Experiment, test, iterate; simulated data first, then beta-user data; keep refining after launch.

      Mobile app: Agile (Scrum). The UI evolves with usability testing and can be built fairly independently.

      AI testing: unit tests for model components, behavioural tests ("learns wake-up time within 2 weeks"), A/B tests, safety tests (never learns to ignore security alerts), and a large beta programme.

      Security-first: threat modelling in design, security code reviews every sprint, penetration testing before each release, automatic security updates after launch.

      🎯 Key takeaways

      No one size fits all. Different projects need different models.
      Requirements drive everything. Poor elicitation sinks projects whatever the model.
      Stakeholders conflict. Technical skill isn't enough; you must negotiate priorities.
      Risk decides rigour. High-risk projects need Spiral, V-Model or formal methods.
      Flexibility vs structure. Agile isn't right for everything; Waterfall isn't wrong for everything.
      Real life is messy. Complex projects often need hybrids.
